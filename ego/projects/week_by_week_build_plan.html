Week by week build plan for semantic code review assistant

Phase 1 — foundations
Week 1 Understand the pieces, set up the environment

Goal: by end of week, you can embed a piece of code and retrieve similar code from a toy dataset. Nothing connected yet — just proof the core idea works.

  • Read Jay Alammar's illustrated BERT (understand what an embedding actually is)
  • Install: Python 3.11, Docker, Cursor, create a GitHub account + test repo
  • Run ChromaDB locally, embed 20 random sentences, query them — see what comes back
  • Load microsoft/codebert-base via sentence-transformers, embed 5 code snippets
  • Write a tiny script: given a code string, find the most similar from a list of 10 — print cosine similarity scores
  • Set up DEVLOG.md — write your first entry tonight
End state: a Python script that takes a code snippet, embeds it with CodeBERT, queries ChromaDB, returns top 3 similar snippets with scores
Week 2 Build the ingestion pipeline

Goal: by end of week, ChromaDB is populated with real bugfix patterns from a real GitHub repo. The knowledge base exists.

  • Install PyGithub, get a GitHub personal access token
  • Write fetcher.py: fetch all closed PRs from a target repo (start with psf/requests — small, well-labelled)
  • Filter PRs: keep only those with "fix", "bug", "patch" in title or labels
  • Write chunker.py: parse raw diff strings, split by @@ markers, extract removed lines + 5 lines of surrounding context
  • Handle rate limits: check X-RateLimit-Remaining header, sleep when needed — write this in DEVLOG
  • Write embedder.py: embed each hunk, store in ChromaDB with metadata (pr_number, pr_title, pr_url, fix_preview)
  • Also store raw PR data in PostgreSQL using psycopg2
  • Run it end to end — verify ChromaDB has 100+ entries
End state: run python ingest.py psf/requests and ChromaDB fills up with real bugfix hunks. Query it manually and get back relevant results.
Phase 2 — online pipeline
Week 3 Webhook + retrieval (hardest week)

Goal: by end of week, opening a PR on your test repo triggers your FastAPI server, retrieves similar bugfixes, and prints them to your terminal. No LLM yet — just raw retrieval working end to end.

  • Build main.py in FastAPI: one POST endpoint /webhook that receives GitHub events
  • Install ngrok, expose localhost:8000, register as GitHub webhook on your test repo
  • Parse the PR payload: extract the diff URL, fetch the actual diff, run it through your chunker
  • For each hunk: query ChromaDB, collect matches above similarity threshold (start with 0.75)
  • Print matches to terminal with PR number and similarity score — verify they make sense
  • Move processing to a FastAPI BackgroundTask so webhook responds in under 1 second
  • This week will break a lot — budget an extra day, write every failure in DEVLOG
End state: open a PR on your test repo → terminal shows retrieved bugfix matches within 5 seconds
Week 4 LLM review generation + GitHub comment

Goal: by end of week, a real comment appears on a real PR automatically. This is your first full end-to-end demo moment.

  • Install Ollama locally, pull Mistral — test it with a basic prompt (free, no API key)
  • Write reviewer.py: takes retrieved hunks, formats a prompt, calls Mistral, gets review text back
  • Prompt structure: new code + 3 similar past bugfixes + "explain the risk in 3 bullet points"
  • Write commenter.py: POST to GitHub API /repos/{owner}/{repo}/pulls/{n}/reviews with the review text
  • Wire everything together in main.py: webhook → chunk → retrieve → review → comment
  • Open a PR with obviously suspicious code — watch the comment appear
  • Tune: if comment is too verbose, tighten the prompt. If retrieval misses obvious things, lower threshold.
End state: push a PR → automatic comment appears on GitHub with specific risk explanation and reference to past bugfix PR
Phase 3 — polish and deployment
Week 5 Run on real repo + measure precision

Goal: system runs on a real open source repo with 6 months of history. You have a precision number you can cite in interviews.

  • Re-run ingestion on a larger repo: fastapi/fastapi or django/django (more bugfix PRs)
  • Handle edge cases that break: empty diffs, binary files, config-only changes — add file extension filter
  • Handle one-line hunks: expand context by fetching surrounding file lines via GitHub API
  • Manually evaluate precision: take 20 retrieval results, check if they are genuinely relevant — write down your number
  • Adjust similarity threshold based on what you find — document the before/after in DEVLOG
  • Test edge cases: PR with 0 code changes, PR with 50 hunks, PR in a non-Python file
End state: system ingested a real repo, retrieval precision measured and documented, edge cases handled
Week 6 Docker, deploy, README, demo video

Goal: anyone can run your project with one command. It is live on the internet. You have a 3-minute demo video recorded.

  • Write docker-compose.yml: three services — FastAPI app, PostgreSQL, ChromaDB
  • Test: docker-compose up from scratch on a clean folder — fix everything that breaks
  • Deploy FastAPI to Railway (free tier) — point GitHub webhook to the live URL, not ngrok
  • Draw architecture diagram in Excalidraw — save as PNG, add to repo
  • Write README: problem → architecture → design decisions → how to run → example output
  • Record Loom demo (3 min): show the repo, push a PR live, watch comment appear, explain what happened
  • Add demo video link to README and to your resume
End state: public GitHub repo, live deployed system, 3-min Loom demo, clean README with architecture diagram
Week 7 (buffer) Interview prep — explain every decision out loud

Goal: you can talk about this project for 30 minutes without notes. Every design decision has a reason you can state clearly.

  • Write answers to all 8 interview questions (listed below) — then say them out loud, not just read them
  • Do 2 mock interviews on Pramp where you explain only this project
  • Apply to all 8 roles if not done already — deadline check on all of them
  • Update resume: add project with 3 bullet points (what it does, stack, one measurable result like precision %)
  • Fix anything in the project that you cannot explain — if you don't understand why a line of code exists, rewrite it until you do
End state: you can answer "walk me through your project" cold, in under 2 minutes, clearly

The 8 interview questions to prepare

  1. Walk me through your architecture
  2. Why CodeBERT over regular BERT or text-embedding-ada?
  3. Why hunk-level chunking? Why not file-level?
  4. Why not just use SonarQube or GitHub Copilot?
  5. What was the hardest bug you hit?
  6. How did you measure retrieval quality?
  7. What breaks at 100x scale?
  8. What would you do differently with 3 more months?
